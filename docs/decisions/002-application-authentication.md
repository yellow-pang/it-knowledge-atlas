# ADR 002: 개인 모바일 접근과 앱 자체 인증

- 상태: 앱 로그인·세션 구현; 운영 HTTPS·외부 접근과 실기기 검증은 미완료
- 날짜: 2026-11-01
- 대상: 개인 사용자 한 명의 온라인 우선 MVP

## 배경과 결정

5-A에서는 기존 Mac mini의 Cloudflare Tunnel을 공유하고 Cloudflare Access Free로 외부 접근을 보호하는 방식을 조건부로 추천했다. 5-B 운영 문서는 앱에 인증이 없으므로 외부 공개 전 Access를 필요 조건으로 적었다. 이는 배포 제안이었고 Access 설정이나 외부 공개가 완료됐다는 뜻은 아니다.

5-C에서는 개인이 스마트폰에서 자주 학습할 때의 사용 편의성을 고려해 **앱 자체 로그인과 서버 측 인증·인가**를 채택한다. Cloudflare Access는 필수가 아니다. 결정 당시 코드는 인증 없이 개인 진도 조회와 복습 저장이 가능했으며, 이후 5-C-1에서 앱 인증을 구현했다. 로그인 구현과 보호 검증 전에는 앱을 Tunnel에 연결해 외부 공개하지 않는다.

기존 Mac mini Tunnel을 재사용하고 Cloudflare Free Tier 안에서 추가 월 사용료 없이 운영하는 것을 목표로 한다. 실제 계정 플랜·기존 Tunnel 경로·도메인 비용과 충돌 여부는 외부 연결 전 확인한다. Tunnel은 연결 경로이며 로그인이나 인가를 대신하지 않는다. 기존 서비스에 대한 Tunnel·DNS·Access 변경은 이 결정에 포함되지 않는다.

## 선택의 결과

| 관점 | 이전 제안: Cloudflare Access | 현재 결정: 앱 자체 로그인 |
| --- | --- | --- |
| 편의와 범위 | 앱 앞단에서 인증 정책을 관리하지만 외부 인증 화면과 세션에 의존한다. 실제 불편 정도는 기기별로 검증해야 한다. | 앱 안에서 개인의 로그인 흐름과 세션을 조정할 수 있다. 삼성 인터넷에서의 편의성은 아직 검증하지 않았다. |
| 운영과 비용 | Free 범위 내에서 별도 인증 계층을 이용할 수 있으나 계정·정책 관리가 필요하다. | 별도 유료 인증 서비스 없이 구현할 수 있으나 구현·운영·보안 검증 부담이 생긴다. |
| 보안 책임 | Access 정책과 원본 우회 경로를 안전하게 관리해야 한다. | 인증, 세션, 요청별 인가, 공격 방어와 복구를 앱 운영자가 책임진다. 로그인 화면이나 루프백 바인딩만으로 보호가 완료되지는 않는다. |

이 결정은 IT 지식 학습과 기술사 대비를 위한 학습 루프 및 직접 개발·운영하며 배우는 목표를 유지한다. 회원가입, 다중 사용자, 소셜 기능 등은 MVP에 추가하지 않는다. 인증은 복잡한 플랫폼을 전제로 하지 않으며 구현 내용은 아래에 기록한다.

## 후속 구현 요구사항

다음은 결정 당시 요구사항이다. 구현 결과는 아래 5-C-1 절을 따르며 운영·실기기 검증은 완료되지 않았다.

- 인증되지 않은 요청에는 개인 진도·복습 이력 등 개인 학습 데이터와 상태 변경 기능을 제공하지 않는다. 페이지 렌더링, 서버 데이터 접근, API를 서버에서 기본 거부하고 요청마다 검사한다. 현재 `POST /api/reviews`와 개인 데이터가 포함된 오늘 화면을 포함해 모든 경로를 목록화한다. 로그인에 필요한 최소 경로는 예외로 허용하되 보호하고, 정적 콘텐츠 공개 범위도 명시적으로 결정한다. 인증 실패 시 개인 정보가 응답·캐시·로그에 남지 않도록 한다.
- 개인 한 명을 위한 최소 로그인과 로그아웃을 제공하고 공개 회원가입을 두지 않는다. 인증 수단과 자격 증명의 최초 설정·변경·분실 시 복구를 구현 전에 결정한다. 비밀번호를 쓰면 강한 비밀번호와 검증된 비밀번호 해시를 사용하며 평문이나 비밀값을 저장소·로그에 남기지 않는다. 인증 실패에 대한 응답과 시도 제한을 설계해 무차별 대입을 억제하고 잠금에 따른 본인 복구 방법도 마련한다.
- HTTPS를 사용하고 예측 불가능한 세션 식별자, 로그인 시 세션 재발급, 만료와 서버 측 무효화·로그아웃을 마련한다. 쿠키에는 `Secure`, `HttpOnly`, 적절한 `SameSite`와 최소 범위를 적용한다. 유휴·절대 만료 시간과 재인증 조건은 보안과 재방문 편의를 함께 고려해 정한다. 쿠키 기반 상태 변경 요청은 로그인·로그아웃을 포함해 CSRF 방어를 적용하고 `SameSite`만을 유일한 방어로 가정하지 않는다.
- 삼성 인터넷 실제 기기에서 최초 로그인, 비밀번호 관리자·자동 완성, 재방문 시 세션 유지, 만료 후 재로그인, 로그아웃과 저장 실패를 확인한다. 앱 전환이나 브라우저 종료 뒤의 동작과 접근성도 검증한다. 세션 만료 중 평가 저장이 실패하면 성공으로 표시하지 않고 재인증 후 안전한 재시도 방법을 제공한다. 현재 요청 ID는 화면 이탈·새로고침 뒤 유지되지 않으므로 재로그인 과정에서 중복 이력이 생기지 않도록 설계·시험한다.
- 외부 연결 전 미인증 페이지·API 직접 호출, 세션 변조·만료·로그아웃, CSRF, 반복 로그인 실패, 보호 경로의 캐시 및 원본 우회 가능성을 시험한다. 서버 오류나 세션 저장소 장애에도 인증을 우회하지 않게 한다. 기존 운영 Compose의 앱 상태 확인은 현재 `/`의 HTTP 성공 응답을 사용하므로 로그인 도입 시 개인 데이터를 노출하지 않으면서 실제 상태를 확인하도록 함께 검토한다.
- 비밀정보 주입·회전, 세션 폐기, 보안 업데이트, 최소한의 접근·인증 실패 기록과 이상 징후 확인을 운영 절차로 마련한다. 로그에 비밀번호·세션·개인 기록을 남기지 않는다. DB 계정 분리와 Mac 외부 백업·격리 복원 요구사항은 그대로 유지한다.

## 5-C-1 구현

단일 환경 설정 계정의 비밀번호를 Node.js 내장 scrypt로 검증하고, 무작위 세션 토큰의 해시와 만료를 PostgreSQL에 저장한다. 별도의 인증 프레임워크는 사용하지 않는다. 로그인 제한은 DB 트랜잭션으로 직렬화하며 IP와 입력 ID를 구분하지 않고 전역으로 실패를 누적해 5회 실패 후 새로운 로그인을 15분 차단한다. 고의적인 실패로 본인 접속도 막힐 수 있으며 초기에는 이 한계를 감수한다. 동일 출처 검증과 SameSite 쿠키를 함께 사용한다. 절대 만료 기본 30일이며 유휴 만료는 사용하지 않는다. 실기기 및 운영 HTTPS 검증은 후속 작업이다.
