# ADR 001: 데이터베이스와 검색 확장

- 상태: 채택. Mac mini 및 OrbStack 운영 적합성은 검증 전
- 날짜: 2026-11-01
- 대상: 개인용 온라인 우선 MVP와 장기 검색 방향

## 배경과 결정

기존 설계의 SQLite 선택은 단일 사용자, 적은 데이터와 별도 DB 서버 없는 간단한 운영에 적합했다. 현재는 OrbStack을 이미 사용하고 있으며 관계형 검색, Markdown 인덱싱, 의미 검색과 답안 이력의 장기 활용이 명시적 목표다. 이를 고려해 **PostgreSQL을 초기 DB로 채택한다**. SQLite로도 목표를 달성할 수 있고 현재 MVP만을 보면 PostgreSQL이 필수는 아니다. PostgreSQL은 별도 프로세스, 자원 사용, 접근 통제, 업그레이드 및 복구 연습 비용을 수반한다. 설계 채택과 별개로 Mac mini 및 OrbStack의 실제 운영 적합성은 검증 전이다. 자원·재시작·복구 검증 등에서 중대한 문제가 확인되면 이 결정을 재검토한다. 이 결정 당시에는 DB가 구현되지 않았다. 이후 개발용 PostgreSQL 연결을 구성했으며 운영 적합성은 여전히 검증 전이다.

## 비교

| 관점 | SQLite + FTS5 + 벡터 확장 | PostgreSQL + pgvector 후보 |
| --- | --- | --- |
| 초기 비용 | 서버 없이 파일과 라이브러리로 시작. FTS5 포함 여부와 확장 로딩·배포 호환성 확인 필요 | 별도 DB 컨테이너, 계정, 연결, 영속 볼륨과 백업 구성이 필요. OrbStack 경험은 학습 비용을 낮추지만 운영을 없애지는 않음 |
| 개인 학습 데이터 | 트랜잭션과 소규모 개인 기록에 충분. 한 번에 하나의 쓰기 작업으로도 현재 사용에는 대체로 충분 | 트랜잭션과 제약 조건, 복수 연결을 제공하나 지금은 부하 때문에 필요한 것은 아님 |
| 텍스트·관계 검색 | SQL 관계 질의와 FTS5가 가능. FTS 색인과 원본 동기화, 토크나이저 구성 필요 | 관계형 질의, 텍스트 검색과 `pg_trgm`을 한 DB에서 사용 가능. 검색 사본 동기화와 한국어 품질 검증은 여전히 필요 |
| 벡터·하이브리드 | 예를 들어 `sqlite-vec` 같은 별도 확장을 평가할 수 있음. 배포·안정성·API 변경 및 드라이버 호환성을 확인해야 함 | `pgvector` 확장으로 SQL에서 관계 필터와 벡터 검색을 함께 검토하기 쉬움. 확장 버전·호환성·색인 운영과 품질 평가는 필요 |
| 백업·복구 | 일관된 온라인 백업 등으로 단일 DB를 보관·이동하기 쉬움. WAL을 포함한 안전한 절차 필요 | 볼륨 외 별도의 논리 백업·복원, 역할·확장 관리와 버전 호환 확인 필요 |
| 기술 부채 | 현재 가장 단순하지만 이후 선택한 벡터 확장·드라이버가 환경과 맞지 않을 수 있고 DB 전환 시 스키마·질의·데이터 이관 필요 | 검색 가능성 때문에 서버 관리 부담을 선불로 지며 실제 검색 수요가 없으면 과잉일 수 있음. PostgreSQL 전용 쿼리·확장에 대한 결합도 발생 |

SQLite FTS5의 기본 `unicode61`은 문자 분류 기반이며 trigram 토크나이저도 제공한다. 별도 벡터 확장은 SQLite의 기본 기능이 아니다. PostgreSQL `simple` 사전 역시 한국어 형태소 분석을 제공한다고 가정할 수 없다. 어느 선택도 한국어 검색 품질을 자동으로 해결하지 않는다. [SQLite FTS5](https://www.sqlite.org/fts5.html), [sqlite-vec 프로젝트](https://github.com/asg017/sqlite-vec), [PostgreSQL 사전](https://www.postgresql.org/docs/current/textsearch-dictionaries.html).

## MVP와 후속 범위

MVP DB에는 진도와 추가형 복습 이력 및 중복 요청 방지 정보만 둔다. 개인 데이터는 유실 시 Markdown에서 재생성할 수 없으므로 백업 대상이다. 콘텐츠·관계·출처는 Markdown 등의 버전 관리 파일이 원본이다. 초기 제목·별칭 검색과 관계 이동은 소규모 원본을 직접 읽어 처리하고 DB에 콘텐츠 사본을 강제하지 않는다. 검색 색인, pgvector 설치, 임베딩 생성·저장, 벡터 인덱스, 하이브리드 랭킹, 추천, 별도 검색 서버와 작업 큐는 모두 후속이다. 앱 내 답안 저장도 기존 MVP 범위 밖이다.

필요 시 Markdown에서 DB로 재생성 가능한 검색 사본을 만든다. 안정적 콘텐츠 ID와 Git 리비전, 정규화된 입력 해시를 구분한다. 콘텐츠·관계의 검증과 원자적 활성화, 삭제 처리, 실패 표시, 재실행·전체 재구축과 개인 기록 보존이 필요하다. 임베딩을 추가할 때 모델·버전·차원·청크·해시를 기록하고, 본문 또는 모델 변경 시 재생성한다. 각 모델의 벡터를 혼합 비교하지 않고 실제 한국어 질의로 품질·비용을 측정한다. `pgvector`의 정확 검색과 근사 인덱스는 성능·재현율 절충이 있으므로 규모와 측정 결과를 확인한 뒤 선택한다. [pgvector 공식 문서](https://github.com/pgvector/pgvector).

## OrbStack 운영과 검증

개발·운영 DB는 별도 인스턴스, 볼륨, 자격 증명과 설정으로 분리하고 포트 충돌과 다른 프로젝트 자원 경쟁을 피한다. DB 포트는 외부에 공개하지 않는 구성을 우선하며 앱 실행 위치에 따라 내부 네트워크 또는 로컬 바인딩을 선택한다. 포트 미게시만으로 모든 접근이 차단된다고 가정하지 않고 실제 인터페이스·경로를 점검한다. PostgreSQL 이미지의 버전·아키텍처, 볼륨 경로와 업그레이드 절차는 실제 구성 시 확인한다. OrbStack의 컨테이너 실행·네트워크 기능이 DB의 백업이나 부팅 후 정상 복구를 대신하지는 않는다. [OrbStack 컨테이너 네트워크](https://docs.orbstack.dev/docker/network), [OrbStack 볼륨](https://docs.orbstack.dev/docker/file-sharing).

실제 운영 전에 다음을 검증한다.

- 기존 프로젝트와 포트·컨테이너 이름·볼륨이 충돌하지 않고 메모리·디스크 여유가 충분한지 확인한다.
- 개발이 운영 DB에 연결되지 않는지, DB 외부 접근이 차단되고 앱 계정 권한이 최소인지 확인한다.
- OrbStack 및 Mac 재시작 후 DB 준비, 앱 재연결과 최근 기록 보존을 시험한다.
- `pg_dump` 백업을 Mac 외부에 보관하고 별도 DB·볼륨으로 복원하여 최근 복습 이력, 역할·설정과 콘텐츠 리비전의 대응을 확인한다. 단일 DB 덤프에 전역 역할이 포함된다고 가정하지 않는다.
- PostgreSQL 이미지 업데이트·주 버전 업그레이드와 향후 확장 설치·복원의 절차와 호환성을 확인한다. 백업 주기와 허용 손실량은 사용자가 정한다.

결정 이후 개발 환경 구성과 연결·컨테이너 재시작 후 데이터 유지가 확인되었다. 이는 운영 적합성 검증을 대신하지 않는다. 실제 개인 기록 저장 전 준비는 [DB 사용과 운영 준비](../database-operations.md)를 따른다.
