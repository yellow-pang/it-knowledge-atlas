# Mac mini 운영 배포

이 구성은 병합 후 검증된 main 커밋으로 실행한다. 5-C-2에서 최초 운영 배포와 기본 외부 접속을 확인했다. 기존 OrbStack 방식에 맞춰 앱과 PostgreSQL 16을 별도 Compose 프로젝트와 네트워크로 실행한다. 앱은 컨테이너 안의 `0.0.0.0:3002`에 바인딩하고 Mac에서는 `127.0.0.1:3002`에만 게시한다. DB는 호스트 포트를 게시하지 않는다. OrbStack의 다른 컨테이너 접근 경로까지 차단한다고 가정하지 않는다. 앱 자체 로그인을 사용하며 진단 API는 운영에서 404를 반환한다. Cloudflare Access는 필수 조건이 아니다. [인증 전략 결정 기록](decisions/002-application-authentication.md)을 따른다.

배포 때 필요한 환경 변수와 검증 결과는 [운영 배포 설정·검증 점검표](deployment-checklist.md)를 따라 비밀값 없이 별도 기록한다.

## 최초 배포와 갱신

1. 병합된 main의 검증된 커밋을 운영용 체크아웃에서 확인하고, 기존 서비스·포트·디스크 여유를 확인한다. 다른 Compose 프로젝트나 개발 DB를 사용하지 않는다. 이 문서의 명령은 해당 체크아웃에서 실행한다.
2. 최초 설정 시에만 `.env.production.example`을 `.env.production`으로 복사하고 `chmod 600 .env.production`을 실행한다. **기존 운영 환경 파일은 덮어쓰지 않는다.** DB 비밀번호 두 개는 **서로 다른 긴 영문·숫자 무작위 값**으로 설정한다. README의 비밀번호 해시 생성 절차에 따라 별도의 앱 로그인 해시와 계정 ID를 설정한다. `APP_ORIGIN`에는 실제 접속 주소의 HTTPS 출처만 설정한다(예: `https://atlas.example.com`, 경로와 마지막 `/` 제외). 포트가 있으면 포함한다. 로그인·로그아웃·복습 저장의 Origin 검사가 이 값과 정확히 일치해야 한다. `AUTH_SESSION_DAYS`는 1~30일이다. 셸 환경에 같은 변수명이 설정돼 있으면 Compose의 env-file보다 우선할 수 있으므로 제거한다. 파일과 자격 증명은 Git·로그에 넣지 않고 안전하게 보관한다. 포트가 사용 중이면 `ATLAS_PORT`를 비어 있는 루프백 포트로 변경한다.
3. `docker compose --env-file .env.production -f compose.production.yaml build`로 고정된 커밋의 앱과 Markdown을 빌드한다. Dockerfile은 기본 `npm run build`(Turbopack)를 사용하며 5-C-2 운영 이미지에서 성공했다. `docker compose --env-file .env.production -f compose.production.yaml up -d --wait db`로 전용 DB를 시작한다.
4. 프로젝트 이름 `it-knowledge-atlas-prod`, 서비스 `db`, DB `atlas_prod`, 계정 `atlas_owner`가 맞는지 확인한다. `docker compose --env-file .env.production -f compose.production.yaml run --build --rm migrate`를 실행한다. `--build`는 이전 마이그레이션 이미지가 남아 있어도 현재 커밋으로 다시 빌드하기 위해 필요하다. 마이그레이션은 내부 호스트와 DB·계정을 검사하고 앱 계정에 필요한 테이블 권한을 부여하고 해당 자격 증명으로 실제 연결을 확인한다. 기존 비밀번호와 환경 파일이 다르면 실패하며 자동 변경하지 않는다. 운영 DB를 개발 명령이나 통합 테스트 대상으로 사용하지 않는다. 스키마 변경 전 백업하고 변경 내용을 검토한다.
5. `docker compose --env-file .env.production -f compose.production.yaml up -d --wait app`을 실행한다. `docker compose --env-file .env.production -f compose.production.yaml ps`와 루프백의 `http://127.0.0.1:3002/api/health`로 프로세스 상태를 확인한다. 다른 포트를 선택했다면 주소를 바꾼다. 운영 모드에서는 Secure 쿠키와 HTTPS 출처 검사를 사용하므로 루프백 HTTP에서 로그인·학습 기능을 확인할 수 없다. 별도 격리 HTTPS 환경에서 로그인과 학습·복습을 검증한다. `/api/health`는 개인 데이터를 반환하지 않는다. 상태 확인은 앱 HTTP 응답과 DB 준비 상태를 나타내며 모든 기능의 정상 동작을 보장하지 않는다.
6. 콘텐츠 변경도 검증·병합된 커밋으로 위 빌드와 마이그레이션 및 앱 시작 절차를 반복한다. 콘텐츠는 이미지에 포함되며 실행 중 파일 변경이 반영되지 않는다. DB 볼륨과 개인 기록은 빌드로 초기화되지 않는다. 적용 커밋을 백업과 함께 기록한다.

DB 최초 생성 후 환경 파일만 바꿔서는 DB 비밀번호가 바뀌지 않는다. 앱 계정이 이미 있으면 마이그레이션은 비밀번호를 변경하지 않는다. 자격 증명 교체는 DB의 해당 역할과 환경 파일을 함께 변경하고 재연결을 확인한다. `down -v`, 볼륨 삭제, 초기화는 사용하지 않는다. 컨테이너 재시작 정책은 Mac 및 OrbStack 자동 기동을 보장하지 않는다.

## 백업과 복원

볼륨은 백업이 아니다. 백업 주기와 허용 손실량을 정하고 암호화된 Mac 외부 저장소에도 보관한다. 아래 예시는 접근 제한된 디렉터리에 덤프를 저장한다. 파일에는 개인 기록이 포함된다. 대상 DB와 출력 위치를 확인하고 기존 백업을 덮어쓰지 않는다.

```sh
umask 077
mkdir -p "$HOME/atlas-backups"
chmod 700 "$HOME/atlas-backups"
( set -C; docker compose --env-file .env.production -f compose.production.yaml exec -T db pg_dump -U atlas_owner -d atlas_prod -Fc > "$HOME/atlas-backups/atlas-$(date +%Y%m%d-%H%M%S).dump" )
```

명령 성공 여부와 파일 크기를 확인하고 실패한 덤프는 백업으로 취급하지 않는다. PostgreSQL 버전·배포 커밋과 콘텐츠 리비전을 별도 기록한다. `pg_dump`는 전역 역할을 포함하지 않는다. 복원은 별도의 빈 PostgreSQL 16 DB와 볼륨에서 `pg_restore --no-owner --no-privileges -U <복원계정> -d <격리DB> <백업파일>`로 수행하고 마이그레이션, 최근 복습 이력 및 앱 조회를 확인한다. 역할·권한은 별도로 재구성한다. 운영 DB에 덮어쓰지 않는다. 운영 DB에는 이미 개인 기록이 있으나 Mac 외부 보관과 실제 격리 복원은 미확인이다. 데이터 보존을 위해 5-D에서 우선 확인한다.

5-B에서는 테스트 덤프를 같은 테스트 인스턴스의 별도 빈 DB에 복원해 복습 이력 건수를 확인했다. 운영 백업의 별도 볼륨·인스턴스 복원, 복원된 앱 연결과 Mac 외부 보관은 미검증이다.

## 5-C-2 배포와 검증 결과

2026-11-01 기준 **5-C-2 운영 배포와 기본 접속 확인을 완료**했다. 배포 기준은 main의 `bb2e98b`이며, 이 문서의 후속 변경 자체가 운영 앱에 반영됐다는 뜻은 아니다.

- 운영 이미지 빌드와 전용 DB의 학습·인증 마이그레이션, 앱·DB 정상 상태를 확인했다. 사용자가 기존 Tunnel에 단일 단계 서브도메인과 DNS 경로를 추가했다.
- 외부 HTTPS에서 로그인 화면, 미인증 학습 화면의 로그인 이동, 미인증 복습 API 거부 및 운영 진단 API 404를 확인했다. 사용자는 기본 사용과 로그아웃 후 로그인 화면 이동을 확인했다. 운영 DB에서는 기록 내용을 조회하지 않고 복습 이력과 학습 상태의 존재만 확인했다.
- 별도 임시 DB와 로컬 HTTPS에서 로그인, Secure·HttpOnly 쿠키, 학습·시험 연계 화면, 복습 저장, 세션 재사용, 로그아웃 후 API 차단과 다른 출처 거부를 확인했다. 임시 DB 결과를 운영 환경 전체 검증으로 간주하지 않는다.
- 기존 운영 컨테이너가 계속 실행 중인 것은 확인했으나 기존 서비스의 전체 기능은 검증하지 않았다. Cloudflare 계정 플랜·결제 설정과 도메인 비용은 미확인이므로 무료 운영 여부는 계정에서 확인해야 한다. 일반 스크립트 요청은 403을 받았고 브라우저 사용자 에이전트 요청은 정상 응답했으며 원인 정책은 미확인이다.

남은 작업은 삼성 인터넷 실기기의 전체 동선·장기 세션·이동 중 사용, 운영 백업과 별도 DB·볼륨 복원, Mac 및 OrbStack 재부팅 후 복구다. 실제 외부 인증 쿠키 속성, 다른 접근 경로의 우회 가능성, 저장 실패와 복구도 추가 확인한다.

## 인증 운영

운영 쿠키는 Secure이므로 HTTPS에서만 전송된다. `APP_ORIGIN`은 외부 주소와 정확히 같아야 하며 운영 모드에서 HTTP 출처는 상태 변경에 허용되지 않는다. Tunnel 연결 전에는 별도의 격리 HTTPS 환경에서 로그인·로그아웃·복습 및 CSRF를 확인한다. 실제 서브도메인 연결 시 브라우저의 출처와 `APP_ORIGIN`이 일치하는지 확인하고 정상 로그인·복습 저장 및 다른 Origin의 요청 거부를 검증한다. 환경 파일은 접근 권한을 제한하고 백업 시 비밀로 취급한다. 세션 토큰은 무작위 값이며 별도 서명 비밀키는 필요하지 않다. 로그인 비밀번호를 교체하거나 유출이 의심되면 해시를 교체하고 서버 측 세션을 모두 폐기한다. 제한 해제와 세션 폐기 방법은 [README](../README.md#개인-로그인-설정)를 따른다. 인증 실패의 민감한 값은 기록하지 않으며 외부 공개 전 모니터링과 원본 우회 경로를 점검한다.

로그인 실패 제한은 IP나 ID를 구분하지 않는 전역 카운터이므로 외부인이 반복 실패를 유발하면 본인의 새 로그인도 15분간 차단될 수 있다. 초기에는 이 단순한 방식을 유지하고 실제 사용 중 문제가 생기면 접근 경로와 제한 방식을 재검토한다.
