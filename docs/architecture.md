# 아키텍처와 운영 방향

## 구성

현재 단일 Next.js 애플리케이션이 반응형 개념 목록·상세와 관계 이동을 제공한다. 상세에는 30초 요약과 3분 설명, 개념별 회상 질문과 접힌 핵심 내용이 있다. 반응형 뷰포트 일부를 확인했으며 실제 스마트폰 사용성은 배포 후 검증한다. 서버가 Git으로 관리하는 Markdown 개념 파일을 읽어 필수 값·형식·ID·관계 유형과 참조를 검증한다. Front Matter는 YAML의 부분집합인 JSON 객체로 제한하며 본문은 문단만 렌더링한다. 자세한 작성 방식은 [README](../README.md#개념-콘텐츠-작성)를 따른다. 시험 자료와 개념 관계도 파일에서 검증하며 출처와 버전별로 표시한다. 실제 원문 대조를 마친 개념 연결은 아직 없다. 개인 회상 내용 저장은 구현하지 않았다.

오늘 학습, 복습과 현황을 구현하고 PostgreSQL을 개인 진도와 복습 이력의 원본으로 사용한다. `learning_state`는 개념별 최초·마지막 평가 시각과 다음 복습일을 저장하며, `review_event`는 평가와 규칙 버전을 추가 기록한다. 서버는 콘텐츠 ID를 검증하고 두 테이블을 한 트랜잭션으로 갱신한다. 요청 UUID의 재전송은 기존 이력을 반환하며 같은 ID에 다른 평가를 보내면 거부한다. 콘텐츠가 사라져도 기존 기록은 유지되지만 미연결 기록을 표시하는 화면은 아직 없다. 향후 재생성 가능한 콘텐츠 검색 사본도 담을 수 있다. MVP에는 별도 검색 서비스나 큐가 필요하지 않다. 콘텐츠 파일을 사용자가 웹에서 직접 편집하는 기능은 MVP 밖에 둔다.

로컬 콘텐츠 등록은 CLI에서 Markdown 파일 또는 폴더를 읽고 기존 원본과 함께 검증한 뒤 사용자의 명시적 적용 명령으로 새 파일을 생성한다. 동일 내용은 건너뛰고 기존 파일이나 ID는 덮어쓰지 않는다. 초안은 원본을 보존하며 사람이 필수 정보와 관계를 검토한다. DB에는 접근하지 않는다. 등록 시 검증 실패를 처리하지만 강제 종료와 전원 장애에 대한 여러 파일의 원자적 반영은 보장하지 않는다. 새 콘텐츠의 앱·DB 연계 흐름은 통합 검증이 남았으며 사용·복구 절차는 [콘텐츠 관리 안내](content-workflow.md)에 둔다. 운영 반영에는 콘텐츠를 포함한 재빌드와 배포가 필요하다.

Next.js App Router, React와 TypeScript를 사용하며 Tailwind CSS와 CSS로 화면을 구성한다. shadcn/ui는 필수가 아니며 접근 가능한 기본 구성 요소를 직접 만들기 어려운 경우 필요한 것만 도입한다. PostgreSQL은 기존 OrbStack 경험과 장기 검색 목표를 고려해 초기 DB로 채택했으며 별도 운영 부담을 수반한다. Mac mini와 OrbStack에서의 실제 운영 적합성은 아직 검증 전이다. SQLite는 서버 없이 시작·백업하기 쉬운 실질적 대안이다. 비교와 판단 근거는 [결정 기록](decisions/001-database-selection.md)에 둔다.

## 콘텐츠 동기화와 검색 확장

현재 원본 파일을 읽어 관계 이동을 제공한다. 소규모 제목·별칭 검색과 별칭 필드는 아직 구현하지 않았으며 MVP에서 검토한다. 본문 전문 검색이나 관계형 질의의 필요가 확인되면 동일 DB에 재생성 가능한 검색 사본을 추가한다. Markdown의 안정적 ID와 명시적 관계가 원본이며 Git 커밋 또는 배포 리비전은 콘텐츠 집합의 버전이다. 향후 콘텐츠 유형·별칭과 파일별 정규화 규칙을 명시한 콘텐츠 해시를 도입할 수 있다. 해시는 변경 감지용이지 ID나 검증 상태가 아니다. 개인 기록은 콘텐츠 사본 삭제·재구축의 영향을 받지 않도록 하고 누락 ID는 [학습 모델](learning-model.md)의 방침을 따른다.

후속 인덱싱은 배포 시 또는 명시적 수동 명령으로 전체 파일을 검증한 뒤 변경분을 반영한다. 중복 ID·끊어진 참조·파싱 오류가 있으면 새 버전을 활성화하지 않고 실패와 이전 색인의 리비전을 표시한다. 생성·변경·삭제 및 관계를 한 트랜잭션으로 반영해 재실행 가능하게 하며, 성공 후 리비전과 해시를 기록한다. 콘텐츠 배포와 색인 활성화 시점을 맞추고 불일치 시 이전 콘텐츠·색인을 유지하거나 검색을 비활성화한다. 원본에서 전체 재구축 가능해야 하며 재구축은 개인 기록을 삭제하지 않는다.

한국어 조사·띄어쓰기, 영문 약어와 혼합 표기는 기본 토큰 검색만으로 충분하다고 가정하지 않는다. 초기에는 정규화된 제목·별칭의 정확·부분 일치로 시작하고 실제 질의 예제로 품질을 측정한다. 이후 PostgreSQL `simple` 텍스트 검색과 `pg_trgm` 부분·유사 문자열 검색을 비교할 수 있지만 둘 다 한국어 형태소 분석기가 아니다. 짧은 검색어와 한글 조합형·완성형, 공백·특수문자, 영문 대소문자 및 성능을 검증하고, 필요할 때 형태소 분석기나 별도 검색 도구를 평가한다. [PostgreSQL 사전](https://www.postgresql.org/docs/current/textsearch-dictionaries.html), [pg_trgm](https://www.postgresql.org/docs/current/pgtrgm.html).

임베딩은 아직 생성하지 않는다. 도입 시 콘텐츠 ID·본문/청크의 해시, 청크 방식 버전, 모델명·버전·차원, 생성 시각과 상태를 함께 기록하고, 원본 또는 모델 변경 시 해당 벡터를 무효화해 재생성한다. 서로 다른 모델·차원의 벡터는 혼합 비교하지 않는다. PostgreSQL의 [pgvector](https://github.com/pgvector/pgvector)는 확장 후보이며 처음부터 설치하거나 근사 최근접 인덱스를 만들지 않는다. 키워드와 벡터 결과의 순위 결합, 추천 품질, 임베딩 비용·외부 전송 여부는 실제 자료와 질의로 평가한 뒤 결정한다.

복습은 [MVP의 명시적 규칙](mvp.md)을 사용한다. `ts-fsrs`는 개인화의 필요성과 이력 호환·마이그레이션 비용을 확인한 뒤 검토한다. PostgreSQL 채택은 설계 결정이다. 개인 학습 기록은 개발 DB에 구현했으며 운영 환경은 아직 구축하지 않았다.

## PWA와 연결 실패

첫 MVP는 온라인 우선이며 서버 연결이 필요하다. 연결이 없으면 읽기와 기록 저장을 보장하지 않는다. 기록 저장 응답을 확인하지 못하면 안내하고 현재 화면에서 같은 요청을 재시도할 수 있다. 요청 ID는 새로고침이나 화면 이탈 후 유지되지 않는다. 오프라인 읽기와 복습 기록 동기화는 후속 단계다. 먼저 정상 학습·서버 저장 및 실패 안내를 검증한다.

이후 설치 가능성, 앱 셸과 최근 열어 본 콘텐츠의 제한적 읽기 캐시를 기기별로 검증할 수 있다. 캐시되지 않은 콘텐츠는 오프라인에서 열 수 없음을 표시하고, 콘텐츠 갱신·캐시 무효화 정책을 둔다. 오프라인 복습 기록은 초기에는 지원하지 않는다. 재연결 후 다시 평가한다. 향후 지원 시 기기 내 내구성 있는 대기열, 고유 이벤트 ID, 재시도·중복 방지, 충돌 정책과 동기화 확인을 설계·검증한다.

설치 및 서비스 워커 동작은 브라우저와 기기에 따라 달라 실제 사용 환경에서 확인한다. PWA 설치나 캐시만으로 오프라인 저장이 보장되지는 않는다.

## macOS 개발·운영 분리

동일 Mac mini에서 개발·운영 앱과 PostgreSQL은 별도 프로세스, 설정과 DB 인스턴스·영속 볼륨을 사용한다. OrbStack의 별도 컨테이너를 후보로 하며 이름·포트·볼륨을 다른 프로젝트와 구분한다. 앱이 호스트에서 DB에 접근해야 하면 DB 포트는 필요한 로컬 인터페이스에만 바인딩하고, 같은 컨테이너 네트워크를 쓰면 포트를 공개하지 않는 방식을 우선 검토한다. 실제 접근성은 OrbStack 설정에서 확인한다. DB 계정·비밀번호·접속 정보도 환경별로 분리하며 앱 계정은 필요한 최소 권한만 부여한다. 운영 DB를 Git이나 빌드 산출물에 두지 않고 개발 테스트가 운영 DB를 가리키지 않도록 접속 대상을 확인한다. 운영은 고정된 빌드 산출물을 실행하고 개발 서버와 분리해 업데이트한다.

macOS의 `launchd`와 컨테이너 재시작 정책을 후보로 검토하되 OrbStack 자체 기동, DB 준비 및 앱 연결 순서를 함께 확인한다. 재시작 정책만으로 OS 부팅 후 전체 복구가 보장된다고 가정하지 않는다. 실행 계정의 권한, 로그 위치·회전, 실패 감지와 재시작 후 정상 동작 확인을 운영 절차에 명시한다. OS 재시동, 잠자기 및 전원 장애 후 복구는 실제 환경에서 시험해야 한다. 설정·서버 설치와 배포는 이번 설계 범위가 아니다.

개발 DB의 현재 관리자 계정과 실제 개인 기록을 저장하기 전 필요한 준비는 [DB 사용과 운영 준비](database-operations.md)에 정리한다. 운영 환경은 아직 구축하지 않았다.

## 접근 및 보안

초기에는 신뢰할 수 있는 사설 네트워크 또는 사설 VPN을 통한 접근을 우선 검토한다. 네트워크 격리만으로 모든 접근을 신뢰하지 말고 기기 접근 통제와 인증 필요성을 실제 구성에 맞춰 검토한다. 외부 공개가 필요해지면 HTTPS, 인증·인가, 비밀정보 관리, 업데이트 및 접근 로그를 갖춘 구성을 별도로 설계하고 검증한다. 인터넷 공개 포트는 현재 전제하지 않는다. 비밀정보와 운영 DB는 Git에 넣지 않는다.

## 백업과 복구

콘텐츠는 Git 이력과 원격 저장소로 관리하되 개인 데이터 백업을 대체하지 않는다. 영속 볼륨도 백업이 아니다. 초기에는 [pg_dump](https://www.postgresql.org/docs/current/app-pgdump.html) 논리 백업을 후보로 하며, 복원에 필요한 DB 버전·확장·스키마와 역할 설정, 콘텐츠 리비전을 함께 기록한다. `pg_dump`는 단일 DB를 대상으로 하므로 역할 등 전역 객체는 별도 관리한다. 운영 데이터와 필요한 설정의 백업을 Mac 외부에도 보관하고 암호화·접근 권한을 고려한다. 백업 주기·보존 기간은 허용 가능한 데이터 손실량에 맞춰 정한다. 별도 DB와 볼륨에 복원해 최근 복습 기록과 콘텐츠 리비전·검색 사본 재구축을 확인한다. 운영 DB를 덮어쓰기 전 서비스를 중지하고 기존 데이터를 보존한다. PITR이 필요할 정도의 데이터 손실 허용 범위인지와 자동화는 운영 구현 시 결정한다.

## 확장 경계

필요해지면 답안 시도 테이블, 시험 자료, 오프라인 동기화와 고급 복습 알고리즘을 추가할 수 있다. 지금은 다중 사용자·분산 시스템·외부 자동 수집·AI 평가를 설계의 필수 의존성으로 두지 않는다.
