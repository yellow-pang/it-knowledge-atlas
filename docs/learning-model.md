# 학습 모델

## 분류와 원칙

분야(Domain)는 탐색을 위한 일반 IT 분류다. 컴퓨터 구조·운영체제, 자료구조·알고리즘, 데이터베이스, 네트워크, 소프트웨어 공학, 아키텍처, 보안, 클라우드·인프라, AI·데이터, IT 전략·관리·거버넌스는 시작 후보이며 공식 출제기준이 아니다. 개념은 여러 분야에 속할 수 있고 분류는 학습 과정에서 조정한다. 분야의 이름이나 트리 구조를 개념의 식별자로 쓰지 않는다.

시험 종목(Exam Track)은 정보관리기술사와 향후 컴퓨터시스템응용기술사처럼 시험을 식별한다. 출제기준(Exam Syllabus)은 종목, 공식 자료의 버전 또는 적용 기간, 출처와 확인일을 가진다. 기준의 영역은 해당 버전에 속하며 개념과 다대다로 연결된다. 개정 전후 영역은 별도 항목으로 보존하고 필요할 때 수동으로 대응 관계를 기록한다. 공식 자료의 버전·적용 기간을 확인하지 못하면 미확인으로 남긴다. 일반 분야와 시험 영역 사이에 자동 일대일 대응을 가정하지 않는다.

## 논리적 구성 요소

| 요소 | 역할과 주요 속성 | MVP 저장 제안 |
| --- | --- | --- |
| Concept | 안정적인 ID, 제목, 분야 ID 목록, 정의와 본문, 출처 참조, 검증 상태 | Markdown 파일 |
| Concept Relation | 출발·도착 개념 ID, 관계 유형, 필요한 근거 또는 설명 | 개념 Front Matter의 명시적 관계 |
| Domain | 안정적인 ID와 탐색용 이름 | 소규모 버전 관리 파일 |
| Exam Track | 시험 종목 ID와 이름 | 검증 후 콘텐츠 파일 |
| Exam Syllabus / 영역 | 종목, 버전·적용 기간, 영역 ID, 공식 출처와 확인 상태 | 확인된 경우 콘텐츠 파일; 미확인 값은 비움 |
| Exam Question | 종목, 회차·연도·문제번호, 원문 또는 적법한 참조, 출처·검증 상태 | 검증된 경우 콘텐츠 파일 |
| 개념–문제 연결 | 문제와 개념의 다대다 연결, 필요 시 연결 이유 | 문제 파일의 개념 ID 목록 |
| 문제–출제기준 영역 연결 | 문제와 특정 버전의 영역, 연결 근거·검토 상태 | 확인 가능한 경우에만 문제 파일에 참조; 불확실하면 비움 |
| Learning Progress | 개념 ID, 최초 학습 여부, 현재 다음 복습일과 규칙 버전 | SQLite |
| Review History | 고유 ID, 개념 ID, 평가, 실제 시각, 계산된 예정일과 규칙 버전 | SQLite에 추가 기록 |
| Answer Attempt | 문제 또는 학습 과제 ID, 작성 시각, 본문·키워드, 반복 회차 및 이전 시도 참조 | 후속 SQLite; MVP에서는 저장하지 않음 |
| Source / Verification | 출처명·URL·확인일·필요한 범위, 검증 상태와 검토 근거 | 각 콘텐츠의 메타데이터 또는 공통 출처 참조 |

이는 논리 모델이며 각 항목을 별도 테이블로 만드는 요구가 아니다. 콘텐츠 ID는 변경하지 않고 제목 변경이나 파일 이동에도 개인 기록을 연결한다. 삭제·병합 시에는 기존 ID와 기록을 보존하고 대체 ID를 명시한다. 콘텐츠를 갱신해도 복습 이력을 지우지 않는다. SQLite에는 개인 상태만 두고 콘텐츠와 조합해 읽는다. 이력과 현재 상태는 한 트랜잭션으로 저장한다.

개인 기록이 현재 콘텐츠에 없는 ID를 가리키면 이력을 삭제하지 않고 ‘현재 콘텐츠에서 찾을 수 없는 개념’으로 표시하고 관리 점검 대상으로 남긴다. 일반 학습 현황과 복습 목록에서는 해당 기록을 별도 미연결 항목으로 집계해 유효한 현재 개념 수에 포함하지 않는다. 대체 ID가 있으면 이동을 안내한다. 병합된 기록을 자동으로 합칠지는 추후 결정하며 그 전에는 원래 ID를 보존한다.

```mermaid
erDiagram
    CONCEPT }o--o{ DOMAIN : belongs_to
    CONCEPT ||--o{ CONCEPT_RELATION : from
    CONCEPT ||--o{ CONCEPT_RELATION : to
    EXAM_TRACK ||--o{ EXAM_SYLLABUS : has
    EXAM_SYLLABUS ||--o{ SYLLABUS_AREA : contains
    CONCEPT }o--o{ SYLLABUS_AREA : maps_to
    EXAM_TRACK ||--o{ EXAM_QUESTION : includes
    CONCEPT }o--o{ EXAM_QUESTION : helps_answer
    EXAM_QUESTION }o--o{ SYLLABUS_AREA : may_map_to
    CONCEPT ||--o| LEARNING_PROGRESS : tracks
    CONCEPT ||--o{ REVIEW_HISTORY : records
    EXAM_QUESTION ||--o{ ANSWER_ATTEMPT : practices
```

도식은 주요 관계만 나타낸다. 문제–개념 연결과 문제–출제기준 영역 연결은 별도 판단이다. 후자는 해당 영역이 속한 기준 버전과 연결 근거·검토 상태를 기록하며, 개념 연결만으로 자동 확정하지 않는다. 출처·검증은 개념, 기준, 영역, 문제 및 필요한 관계에 연결할 수 있다. 답안 시도는 문제 외 학습 과제에도 연결할 수 있다.

## 개념과 관계

개념 노트는 한 줄 정의, 30초 요약, 3분 설명을 중심으로 구성요소·동작 원리·장단점·비교·예시·실무 활용·관련 개념·시험 관련성을 필요할 때만 포함한다. 일반 설명을 복사해 시험용 노트를 따로 만들기보다 같은 개념을 참조하고, 시험 관점의 설명이나 목차 힌트만 덧붙인다. 빈 항목은 생략한다.

관계는 ID를 대상으로 명시한다. `prerequisite`는 **이 개념을 배우기 위한 선행 개념**을 가리키는 방향이고, `related`와 `compare`는 관련·비교 대상이다. 실무 사례와 시험 영역·문제는 각 자료에 대한 참조로 구분한다. 대칭 관계도 자동 역방향 생성을 가정하지 않으며 표시 정책은 구현 시 정한다. `[[표시 이름]]`은 작성 편의로 검토할 수 있지만 동명·이름 변경에 대비해 실제 연결은 안정적인 ID로 해석한다. 참조 누락과 중복 ID는 콘텐츠 검사에서 보고한다.

## 출처와 검증

상태는 `draft`(초안), `needs_review`(검토 필요), `verified`(검증 완료)로 구분한다. 검증 완료는 해당 내용과 연결에 대해 적절한 근거를 대조하고 검토자·날짜 또는 검토 기록을 남긴 경우에만 부여한다. AI 작성·보조 여부와 사용 범위는 별도 기록이며 검증 상태를 대신하지 않는다. 출처명, 원본 URL, 확인일, 적용 범위·버전과 필요한 경우 라이선스를 기록한다. 내용 변경 시 영향받은 검증을 재검토한다.

검토 범위를 짧게 명시한다. 예를 들어 ‘회차·문제번호 확인, 원문과 개념 연결은 검토 필요’로 구분한다. 문제나 개념의 검증 상태가 그 원문이나 개념·출제기준 연결의 검증을 자동으로 뜻하지 않는다. 각 연결의 검토 근거와 상태는 별도로 남긴다.

공식 기준의 유효 버전, 회차·문제번호·원문은 신뢰 가능한 자료를 확인하기 전에는 확정하지 않는다. 문제의 출처와 이용 조건을 확인하고 원문을 저장할 권리가 불명확하면 링크와 식별 정보만 사용한다. 외부 서브노트·교재는 허락이나 라이선스 확인 없이 복사하지 않는다.

## 데이터 흐름 예시

예시 개념 `transaction`을 Markdown에 정의하고 분야 `database` 및 선행·관련 개념 ID를 연결한다. 설명의 출처와 검증 상태를 표시한다. 시험 기준과 문제는 공식 근거를 확인했을 때만 별도 항목으로 만들고 같은 개념 ID를 참조한다. 사용자가 내용을 읽고 `기억남`을 선택하면 SQLite 트랜잭션에서 평가 시각과 규칙 버전을 이력에 추가하고 현재 예정일을 갱신한다. 이후 본문을 고쳐도 ID가 유지되므로 과거 이력은 그대로다. 나중에 검증된 문제에 대한 답안을 여러 번 작성하면 각 시도를 독립 기록으로 남겨 개선 과정을 비교할 수 있다. 이 예시는 특정 출제 사실을 주장하지 않는다.
